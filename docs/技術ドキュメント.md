### 使用技術

| 層 | 採用 | 版 |

### 画面を持たないこと

**`/` は説明用の静的ページ1枚だけです。管理画面はありません。**

オーナー様がPCをほぼ使わないため、**操作はすべてLINEのリッチメニューから**行います。
Webで作るはずだった管理画面は、LINE側の機能に置き換えました（要件定義書 F-08・F-20）。

その結果、**ログイン・セッション・認可の実装が一切不要**になっています。
認証に相当するのは「LINEの署名検証」と「オーナーの識別子との一致」の2つだけです。

## 2. 外部サービスとの連携

| サービス | 用途 | 認証 | 無料枠 |
|---|---|---|---|
| LINE Messaging API | 受信・返信・通知・リッチメニュー | チャネルシークレット（署名）＋アクセストークン | **応答は無料／プッシュ200通/月** |
| Supabase | 未対応の記録・設定値 | 秘密キー（サーバー側のみ） | 無料プラン |
| Vercel | ホスティング・定時実行 | — | **定時実行は1日1回** |

### 使っていないもの

| | 理由 |
|---|---|
| **Claude API・その他のLLM** | **AIに文章を書かせない**方針（要件定義書 N-01）。誤った料金・営業時間を案内しないことが最優先のため、応答はすべて定型文 |
| 予約システムとの連携 | 予約が紙の手帳で管理されており、参照できない |
| 決済 | スコープ外 |

### 無料枠から来ている制約

ここは**仕様に直接影響しています。**

| 制約 | 仕様への影響 |
|---|---|
| Vercel Cron が**1日1回** | リマインドは朝1回のみ。足りない分を「新規通知に未対応件数を同梱」で補う（F-12） |
| LINEプッシュが**200通/月** | 一斉配信を実装しない。320名へ1回で320通になり、枠を超える |
| LINEの**応答メッセージは無料** | お客様への返信は通数を消費しない。ここに制約がないため、一次応答を厚くできた |

> **プッシュの通数は「送った相手の人数」で数えます。**
> `push(to, [messageA, messageB])` のように複数のメッセージを1回で送っても**1通**です。
> 朝のまとめで「未対応の一覧」と「臨時休業のご報告」を同時に送っているのは、これを利用しています。

## 3. API仕様

エンドポイントは**2本だけ**です。

### 3-1. `POST /api/line/webhook`

LINEからのイベントを受け取る入口。実装：[`src/app/api/line/webhook/route.ts`](../src/app/api/line/webhook/route.ts)

**リクエスト**

| | |
|---|---|
| ヘッダ | `x-line-signature`（必須） |
| ボディ | LINE の Webhook イベント（`{ events: [...] }`） |

**レスポンス**

| 状況 | 返すもの |
|---|---|
| 署名が正しい | `200 { "ok": true }` |
| 署名がない／不正 | **`401 { "error": "invalid signature" }`** |
| ボディが JSON でない | `200 { "ok": true }`（疎通確認で空の本文が届くため） |
| 処理中に例外 | **`200 { "ok": true }`**（下記） |

> ⚠️ **何があっても 200 を返します。**
> エラーを返すと **LINEが同じイベントを再送し続け**、通知が何通も届きます。
> イベントは1件ずつ `try/catch` で囲み、1件の失敗で全体を落としません。
> 失敗は `console.error` に出すだけです（Vercelのログで確認できます）。

**扱うイベント**

| `event.type` | 処理 | 要件 |
|---|---|---|
| `follow` | あいさつとリッチメニューを返す | F-01 |
| `unsend` | `message_id` で記録を削除 | F-14 |
| `postback` | ボタン操作（下表） | F-08・F-10 |
| `message`（`text`） | 振り分け → 自動回答 または 転送 | F-02〜F-07 |
| `message`（`text` 以外） | **種類を記録して必ず転送** | **F-21** |

**postback の `data`**

| `data` | 動き |
|---|---|
| `closed_today` / `closed_tomorrow` | 当日・翌日の臨時休業を設定 |
| `closed_prompt` | 書き方の案内（入力欄に「休業 」を入れてキーボードを開く） |
| `closed_off` | お知らせを取り下げる |
| `done:<id>:<shownAt>` | 1件を対応済みにする |
| `doneall:<listedAt>` | 一覧を出した時点のものを対応済みにする |

> `shownAt` / `listedAt` は**ボタンを出した時刻**です。
> これを持たせることで、「**一覧を見たあとに届いた連絡を、見ずに閉じてしまう**」のを防いでいます（§6-3）。

### 3-2. `GET /api/cron/morning`

毎朝のまとめ通知。実装：[`src/app/api/cron/morning/route.ts`](../src/app/api/cron/morning/route.ts)

**リクエスト**

| | |
|---|---|
| ヘッダ | `Authorization: Bearer <CRON_SECRET>`（必須） |

**レスポンス**

| 状況 | 返すもの |
|---|---|
| 合言葉が正しい・送った | `200 { ok, sent: true, open, closedUntil }` |
| 合言葉が正しい・送らない | `200 { ok, sent: false, open: 0 }` |
| 合言葉がない／不一致 | **`401 { "error": "unauthorized" }`** |

**やること（この順番）**

```
① 対応済みから30日たった記録を削除        （N-08）
② 未対応の一覧と、臨時休業のお知らせを取得
     ← getClosure() が、終わった日のお知らせをここで自動的に消す
③ どちらも無ければ、送らずに終わる        （通数を使わない）
④ あるぶんだけ、1回のプッシュでまとめて送る （1通）
```

**実行時刻**

```json
{ "crons": [{ "path": "/api/cron/morning", "schedule": "0 23 * * *" }] }
```

| | |
|---|---|
| cron 式 | `0 23 * * *`（**UTC**） |
| 日本時間 | 8:00 |
| 実際 | **8時台**（Vercel Hobby は ±59分の誤差がある） |

> **開店10:00には必ず間に合う時刻**を選んでいます。
> 9時台にすると、誤差で10時を過ぎる可能性があります。

### 3-3. スクリプト（エンドポイントではありません）

| | |
|---|---|
| `scripts/setup_richmenu.py` | リッチメニュー画像を生成し、LINEに登録・割り当てる。**納品時に1回実行** |
| `--preview-customer` | 自分のアカウントをお客様用メニューに切り替える（通し確認用） |
| `--restore-owner` | オーナー用メニューに戻す |

画像は Pillow で生成しています（2500×1686・2段×3列）。デザインツールは使いません。
**ボタンの文言を変えたら、画像も作り直す**必要があるためです。

## 4. データベース設計

定義：[`supabase/schema.sql`](../supabase/schema.sql)

> **他のアプリと同じSupabaseプロジェクトに同居しているため、
> テーブル名を `sl_` で始めています。** 新しいテーブルを足すときも、この接頭辞を守ってください。

### 4-1. `sl_inquiries` — 未対応の記録

| 列 | 型 | NULL | 意味 |
|---|---|---|---|
| `id` | uuid | ✕ | 主キー（`gen_random_uuid()`） |
| `line_user_id` | text | ✕ | お客様のLINE識別子 |
| `display_name` | text | ○ | LINEの表示名。**本名とは限らない** |
| `message_text` | text | ✕ | 問い合わせの本文。続きが届くと追記される |
| `message_id` | text | ○ | 送信取消への対応に使う（F-14） |
| `category` | text | ✕ | `availability` / `change` / `complaint` / `other` |
| `received_at` | timestamptz | ✕ | **最初**にご連絡いただいた時刻 |
| `last_contact_at` | timestamptz | ✕ | **最後**にご連絡いただいた時刻（F-16） |
| `handled_at` | timestamptz | ○ | **`null` のあいだが「未対応」** |

**インデックス**

| 名前 | 列 | 用途 |
|---|---|---|
| `sl_inquiries_open_idx` | `(handled_at, received_at)` | 未対応を古い順に取り出す |
| `sl_inquiries_message_idx` | `(message_id)` | 送信取消で元の1件を探す |

> **なぜ `received_at` と `last_contact_at` の2つを持つのか**
>
> 一覧には「いつ最初に来たか」を出したいが、
> **対応済みにしてよいかの判定には「最後にいつ連絡が来たか」が必要**です。
> 1つの列で兼ねようとして実際に不具合が出ました（要件定義書 15-6）。
>
> **確かめたい関係があるなら、確かめられる形でデータを持つ。**

> **`handled_at IS NULL` を「未対応」の定義にしている理由**
>
> `status` 列にせず時刻にしてあるのは、**30日で自動削除する条件に使えるから**です。
> `handled_at < now() - 30日` の1文で消せます。

### 4-2. `sl_settings` — 設定値

| 列 | 型 | NULL | 意味 |
|---|---|---|---|
| `key` | text | ✕ | 主キー |
| `value` | text | ✕ | 値（JSON文字列） |
| `updated_at` | timestamptz | ✕ | 更新時刻 |

いま使っている `key` は**1つだけ**です。

| `key` | `value` |
|---|---|
| `closed_note` | `{"text":"本日は臨時休業をいただきます","until":"2026-11-24"}` |

> **`until`（終わる日）を必ず持たせます。**
> これがあるので、**オーナー様が取り消し操作をしなくても翌日に消えます。**
> `getClosure()` は読み出すたびに期限を見て、過ぎていたらその場で削除して `null` を返します。
>
> 「お知らせの消し忘れで、営業中なのに休業と案内し続ける」——
> これを**手順書ではなく仕組みで起こせなくする**ための列です（要件定義書 15-3）。

### 4-3. 持たないもの

**意図的に保存していません**（要件定義書 N-04）。

```
電話番号　メールアドレス　住所　施術履歴　来店履歴　会話の全文
```

やり取りそのものはオーナー様が直接行うため、システムが持つ必要がありません。
**持たないものは漏れません。**

### 4-4. 行レベルセキュリティ

```sql
alter table public.sl_inquiries enable row level security;
alter table public.sl_settings  enable row level security;
```

**RLSを有効にし、ポリシーを1つも作っていません。**

| キー | 読み書き |
|---|---|
| 公開キー（anon） | **できない**（ポリシーがないため全拒否） |
| 秘密キー（`SUPABASE_SECRET_KEY`） | できる |

アプリは**サーバー側からのみ**秘密キーで接続します。
ブラウザに渡るコードからは、このDBに一切触れません。

> ⚠️ `src/lib/db.ts` を**クライアントコンポーネントから import してはいけません。**
> 秘密キーがブラウザに漏れます。ファイル冒頭にその注意書きがあります。

## 5. モジュール構成

```
src/
├── app/
│   ├── page.tsx                      説明用の静的ページ1枚
│   └── api/
│       ├── line/webhook/route.ts     受信の入口（§3-1）
│       └── cron/morning/route.ts     毎朝の通知（§3-2）
└── lib/
    ├── salon.ts        ★ お店の正本（料金・営業時間・所要時間）
    ├── classify.ts       問い合わせの振り分け
    ├── replies.ts        お客様への定型文
    ├── buttons.ts        クイックリプライのボタン定義
    ├── line.ts           署名検証・送信・Flex Message の組み立て
    ├── db.ts             Supabase への読み書き
    ├── closed.ts         臨時休業の日付の読み取りと有効判定
    └── time.ts           日本時間の計算・営業時間判定
```

| ファイル | 責務 | 触るときの注意 |
|---|---|---|
| **`salon.ts`** | **料金・営業時間・所要時間の唯一の出所** | **ここだけ直せば全部に反映される。他のファイルに金額・時刻を書かない** |
| `classify.ts` | 文面 → カテゴリ | **ルールの並び順そのものが仕様。**上から順に判定し、先に当たったものを採用する |
| `replies.ts` | カテゴリ → 文面 | AIに書かせない。すべて定型文 |
| `line.ts` | LINEとのやり取り | `reply` は無料、`push` は通数を消費する |
| `db.ts` | 永続化 | **サーバー専用** |
| `closed.ts` | 臨時休業 | 文中の日付を読み取り、`until` を決める |
| `time.ts` | 時刻 | 日本時間はここに集約。各所で `+9時間` しない |

### `salon.ts` を正本にしている理由

```ts
export const SALON = {
  openTime: "10:00",
  closeTime: "19:00",
  closedWeekdays: [3],              // 水曜
  lastOrder: { color: "16:00", cut: "18:00" },
} as const;

export const DURATIONS = [
  { name: "カット", minutes: 60, label: "約60分", chair: "cut" },
  { name: "カット＋カラー", minutes: 150, label: "約120〜150分", chair: "color" },
  ...
] as const;
```

**案内文は、この定数から組み立てます。**

```ts
export const HOURS_TEXT = `【営業時間】

${SALON.openTime} 〜 ${SALON.closeTime}
定休日：毎週${SALON.closedWeekdayLabel}

※ ${menuNames("color")}は${SALON.lastOrder.color}、...が最終受付となります`;
```

> **以前は案内文に「10:00 〜 19:00」を直書きしていました。**
> 営業中かどうかの判定は `SALON` を見ているのに、案内文は別だったため、
> **`SALON` を直すと「営業中です」と答えながら閉店している**状態になります。
> まだ事故は起きていませんでした。営業時間を一度も変えていなかったからです。
> **「いま壊れていないが、1回直したら壊れる」**ものは、実機で触っても見つかりません（要件定義書 #16）。

**`minutes` を数字で持っているのも同じ理由です。**
「最終受付 ＋ 施術時間 ≦ 閉店」を**計算で確かめられる形**にするためです（§10）。

## 6. 処理の流れ

### 6-1. お客様からメッセージが届いたとき

```
POST /api/line/webhook
　│
　├─ ① 署名検証 … 失敗なら 401（中身は一切見ない）
　│
　├─ ② イベントごとに処理（1件ずつ try/catch）
　│
　├─ ③ 文字以外か？
　│      はい → 種類を記録（［お写真］など）→ カテゴリは other 固定 → ⑥へ
　│      いいえ → ④へ
　│
　├─ ④ オーナーの識別子と一致？
　│      はい → 決まった言葉ならコマンドとして処理して終了
　│
　├─ ⑤ classify(text) で振り分け
　│
　├─ ⑥ autoAnswer() が文面を返す？
　│      はい → そのまま返信して終了（通数は消費しない）
　│      いいえ（転送対象）→ ⑦へ
　│
　└─ ⑦ 転送
        ├─ 同じお客様の未対応が残っている？
        │    はい → そこに追記（未対応は増やさない）＋【追加のご連絡】で通知
        │    いいえ → 新規記録 ＋ 通知（未対応の残り件数を同梱）
        └─ ★ お客様への返信を先に行う（お待たせしないため）
```

> **⑦で「お客様への返信を先」にしているのは意図的です。**
> 通知やDB書き込みが遅れても、お客様の体験を損なわないためです。

### 6-2. 急ぎの用件は、まとめない

```ts
export function canMergeInto(existing: Category, incoming: Category): boolean {
  const urgent = incoming === "change" || incoming === "complaint";
  if (!urgent) return true;
  return existing === incoming;
}
```

未対応は「お客様ひとりにつき1件」にまとめますが、
**「空き状況を聞いていた方が、やっぱりキャンセルしたい」**は別の1件にします。
前の問い合わせに埋めてしまうと、**至急の通知が埋もれる**ためです。

### 6-3. 一覧を見たあとに届いた連絡を、閉じない

対応済みボタンには、**そのボタンを出した時刻**を持たせています。

```ts
const last = Date.parse(inquiry.last_contact_at ?? inquiry.received_at);
const shown = Date.parse(shownAt);
if (last > shown) return { status: "newer", inquiry };   // 閉じずに差し戻す
```

> ⚠️ **ここは文字列で比較してはいけません。**
> Supabase は `2026-11-24T13:00:00+00:00`、JavaScript は `2026-11-24T13:00:00Z` を返します。
> **同じ時刻でも文字列としては別物**なので、必ず `Date.parse` で数値にしてから比べます。

### 6-4. 「返信したら自動で消える」が作れない理由

**LINEは、自アカウントが送ったメッセージをWebhookで受け取れません。**

```
お客様が送る        → Webhookが飛ぶ  ✅
オーナーが返信する   → 飛ばない      ❌
```

そのため「オーナーが返信したことを検知して未対応から外す」は**仕様上できません。**
［✅ 対応済みにする］ボタンを押していただく形にしているのは、この制約からです。

代わりに、**押し忘れても困らないよう**にしてあります。

```
新規通知に「ほかに未対応◯件」を同梱       （F-12）
毎朝8時台に残っているものだけ通知         （F-11）
```

## 7. 環境変数

Vercel → Settings → Environment Variables に登録します。ローカルは `.env.local`。

| 変数 | 取得元 | 用途 |
|---|---|---|
| `LINE_CHANNEL_SECRET` | LINE Developers → チャネル基本設定 | **Webhookの署名検証** |
| `LINE_CHANNEL_ACCESS_TOKEN` | LINE Developers → Messaging API設定（長期） | 返信・通知・リッチメニュー登録 |
| `OWNER_LINE_USER_ID` | チャネル基本設定 → あなたのユーザーID（`U` で始まる） | **通知先と、オーナー判定** |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → API | 接続先 |
| `SUPABASE_SECRET_KEY` | 同上（**secret**） | **サーバー側のみ。絶対に公開しない** |
| `CRON_SECRET` | 自分で生成した長い文字列 | 朝の通知の合言葉 |

> **`OWNER_LINE_USER_ID` を変えると、通知先とオーナー用メニューの両方が切り替わります。**
> 担当者が変わるときは、ここと `setup_richmenu.py` の再実行が必要です。

> ⚠️ `NEXT_PUBLIC_` が付いた変数は**ブラウザに渡ります。**
> URLは公開されても問題ありませんが、**キーに `NEXT_PUBLIC_` を付けてはいけません。**

## 8. セキュリティ

| 対策 | 実装 |
|---|---|
| **Webhookのなりすまし防止** | `x-line-signature` を HMAC-SHA256 で検証。**検証前に中身を見ない** |
| **タイミング攻撃対策** | `crypto.timingSafeEqual` で比較（長さが違うと例外になるので先に長さを確認） |
| 定時実行の保護 | `Authorization: Bearer <CRON_SECRET>` |
| DBへの直接アクセス防止 | RLS有効・ポリシーなし。秘密キーはサーバー側のみ |
| 個人情報の最小化 | 電話・メール・住所・施術履歴を持たない |
| 保存期間 | 対応済みから**30日で自動削除** |
| 鍵の管理 | `.gitignore` で `.env*` を除外。**全履歴を確認済み** |

```ts
// 署名を確かめてから中身を見る
if (!verifySignature(raw, req.headers.get("x-line-signature"))) {
  return NextResponse.json({ error: "invalid signature" }, { status: 401 });
}
```

**確認済み**（[動作確認チェックリスト](./動作確認チェックリスト.md) F章）

```
署名なし・偽の署名でWebhookを叩く  → 401 ✅
合言葉なしで朝の通知を叩く         → 401 ✅
公開リポジトリの全履歴に鍵がない   → ✅
```

## 9. 時刻の扱い

**日本時間の計算は `src/lib/time.ts` に集約しています。** 各所で `+9時間` しません。

| 関数 | 返すもの |
|---|---|
| `jstNow()` | 日本時間の年・月・日・時・分・曜日 |
| `jstDateKey()` | `"2026-11-24"`（日本時間の今日） |
| `jstDateKeyAfter(n)` | n日後 |
| `formatJst(iso)` | `"11/24 22:13"`（通知の表示用） |
| `isOpenNow()` | いま営業中か（定休日・開店前・閉店後を見る） |

### 気をつける点

| | |
|---|---|
| **サーバーのタイムゾーンはUTC** | Vercel上では `new Date().getHours()` が日本時間になりません |
| **cron式もUTC** | `0 23 * * *` が日本時間の8:00 |
| **DBとJSで文字列の形が違う** | `+00:00` と `Z`。**文字列比較は禁止**（§6-3） |
| 臨時休業の `until` は**日付のみ** | 「その日いっぱい」の意味。時刻は持たない |

```bash
npx vitest run
```

**144件**。すべて純粋な関数のテストで、**DBもLINEも叩きません**（モックも不要）。

| ファイル | 件数 | 見張っているもの |
|---|---|---|
| `classify.test.ts` | **79** | 振り分け。**ヒアリングで実際に伺った文面**をそのまま使う |
| `replies.test.ts` | 26 | 文面。言い方・休業のお知らせの位置・文字以外への応答 |
| `line.test.ts` | 14 | 署名検証・Flex Message・要約 |
| `closed.test.ts` | 13 | 日付の読み取り（`12/29〜1/3` → `until` は1月3日） |
| `salon.test.ts` | 12 | **正本の検算**（下記） |

> **半分以上が `classify.test.ts` です。**
> 振り分けの取りこぼしが、このシステムで最も起きやすい壊れ方だからです。
> 実機で10件まとめて見つかったことがあり、そこから全カテゴリを洗い直しました（要件定義書 15-4）。

### `salon.test.ts` が特別な理由

**納品後、オーナー様の新しい料金表を人の手で反映します。** そのときの事故を止めます。

```
・金額は「〜」で幅を持たせる（前髪カットだけ定額でよい）
・3つの注意書きを消さない（ロング／セット割／施術時にご案内）
・案内文の営業時間が SALON と一致している
・定休日・開店前・閉店後は「営業中」にならない
・★ 最終受付 ＋ 施術時間 ≦ 閉店
```

最後の1つはこう書いてあります。

```ts
const close = minutesOf(SALON.closeTime);
for (const d of DURATIONS) {
  const finish = minutesOf(SALON.lastOrder[d.chair]) + d.minutes;
  expect(finish, `${d.name}（${d.label}）が閉店に間に合いません`).toBeLessThanOrEqual(close);
}
```

> **これは実際に破れていました。**
> 「カラー・パーマは17:00が最終受付」も「カット＋カラーは約120〜150分」も、
> **単体ではどちらも正しい**のです。足すと19:30で、閉店19:00を越えます。
> 1文ずつ読んでいる限り、何度読んでも見つかりません（要件定義書 #17）。
>
> **施術時間を1つ延ばすだけで、また破れます。** 人の記憶に頼らず、ここで止めます。

### テストで見つからないもの

**自動テストは「決めたとおりに動くか」しか見ません。**

記録した不具合18件のうち、**自動テストで見つかったものは0件**です。
見つけ方の内訳は要件定義書 15-9 にあります。
**実機で触る／書類を書く／正本と出力を突き合わせる**——この3つが効きました。

## 11. 引き継ぐ人が最初に読むべき3か所

```
① src/lib/salon.ts
     料金・営業時間の正本。ここを理解すれば、
     「どこを直せばお客様への案内が変わるか」が分かる

② src/lib/classify.ts の RULES
     並び順そのものが仕様。上から順に判定する。
     順番を入れ替えると、別のカテゴリに吸われる

③ docs/要件定義書.md 第15章
     見つかった不具合18件と、その学び。
     同じ穴をもう一度開けないために、ここだけは読んでほしい
```

### 変更するときの型

| 変えたいもの | 直す場所 | 確認 |
|---|---|---|
| 料金・営業時間・所要時間 | `src/lib/salon.ts` **のみ** | `npx vitest run src/lib/salon.test.ts` |
| 拾えていない言い方を足す | `src/lib/classify.ts` の `RULES` | `npx vitest run src/lib/classify.test.ts` |
| お客様への文面 | `src/lib/replies.ts` | `npx vitest run src/lib/replies.test.ts` |
| リッチメニューのボタン | `scripts/setup_richmenu.py` → **再実行** | 実機で表示を確認 |
| 通知の見た目 | `src/lib/line.ts` の Flex | 実機で確認（Flexはテストしきれない） |

### やってはいけないこと

| | 何が起きるか |
|---|---|
| 金額・時刻を `salon.ts` 以外に書く | **片方だけ古くなり、誤案内になる** |
| `db.ts` をクライアントから import | **秘密キーがブラウザに漏れる** |
| Webhookでエラーを返す | **LINEが再送し続け、通知が何通も届く** |
| 時刻を文字列で比較 | `+00:00` と `Z` で食い違う |
| `classify.ts` の `RULES` の順番を入れ替える | 別のカテゴリに吸われ、取りこぼす |
| 文字以外のメッセージを `return` で捨てる | **落ちないが、誰にも届かない**（#18） |
