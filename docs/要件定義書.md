## 1. 背景

ヒアリング（全24問・3回）で確認した事実を記載します。

### 1-1. お客様の状況

| 項目 | 内容 |
|---|---|
| 業態 | 個人経営の美容室（スタッフはオーナー1名） |
| 営業時間 | 10:00〜19:00 / 水曜定休（臨時休業 年5〜6回） |
| LINE友だち数 | 約320人 |
| 顧客構成 | **既存客 8割**／新規は月2〜3人 |
| 予約管理 | **紙の手帳**（店内に保管） |

| 問い合わせ件数 | 1日3〜10件／対応に1日40分〜60分 |
| 問い合わせ時間帯 | **夜21〜23時および日曜夜に集中** |

### 1-2. 現状の困りごと

ヒアリングでの発言：

> 「買い物中にLINEが来たら『帰ってから確認してご連絡しますね』と返すんですけど、**それを忘れてしまうことがあって**。翌朝『すみません!!』と謝ることが月に何回かあります。」

> 「電話は出られないときは出なくていいので、そこまで苦ではないんです。**LINEは既読がついてしまう**ので、読んだのに返していないのが気になって……。」

> 「時間というより……**夜、返信のことが頭から離れないのが嫌**なんです。」

## 2. 課題の定義

### 2-1. ヒアリング前の仮説（外れ）

> 同じ質問に繰り返し手作業で返信していることが負担である。

### 2-2. 実際の課題

> **その場で答えられない問い合わせを抱えたまま夜を過ごし、既読のプレッシャーを感じ、ときどき返信を忘れて謝罪することになっている。**

仮説を棄却した根拠：

| 事実 | 意味 |
|---|---|
| 既存客が8割・新規は月2〜3人 | 料金を尋ねる人はそもそも少なく、FAQ自動化の効果は限定的 |
| 問い合わせは夜21〜23時が中心 | 返せない理由は「施術中」ではなく**営業時間外** |
| 「LINEは既読がついてしまう」 | 負担の正体は**作業量ではなく心理的プレッシャー** |

### 2-3. 本システムの目的

**24時間、取りこぼしなく一次対応を行い、オーナーの頭から問い合わせを降ろす。**

FAQへの自動回答は手段であって目的ではありません。**「返信を忘れない」「夜に抱え込まない」**が達成すべき状態です。

そのため本システムの責任範囲は、一次応答を返すところで終わりません。**対応が完了するまで問い合わせを記録し、追いかける**ところまでを含みます。通知を1回送るだけでは、オーナー様が手を離せない状況にあれば結局忘れてしまうためです。

### 6-2. 詳細

#### F-01　メニュー表示

お客様に自由入力をさせず、**ボタンで誘導する**ことで誤解釈を防ぐ。**2種類**を用意する。

**① リッチメニュー（トーク画面の下に常時表示・2段×3列）**

```
┌──────────┬──────────┬──────────┐
│  営業時間  │メニュー・料金│  施術時間  │
│定休日・最終受付│カット／カラー等│どのくらいかかる？│
├──────────┼──────────┼──────────┤
│  空き状況  │ 予約の変更 │その他のご質問│
│オーナーが確認します│キャンセルもこちら│直接おたずねください│
└──────────┴──────────┴──────────┘
```

**② クイックリプライ（自動回答のあとに5件表示）**

続けて別のことを聞きたいときに、もう一度メニューを開かせない。

| 項目 | 内容 |
|---|---|
| 登録方法 | **Messaging API で登録する**（画像生成＋API登録を `scripts/setup_richmenu.py` で自動化） |
| ボタンが送る文面 | F-02〜F-06 が確実に拾える言葉に固定する（例：「空き状況を知りたいです」） |

> **当初「管理画面から設定（開発不要）」としていましたが、API登録に変更しました。**
> ① お客様用とオーナー様用を**出し分ける**必要があるため（F-20）
> ② 「臨時休業を設定」ボタンのような**入力欄に文字を入れた状態でキーボードを開く**動作は、管理画面では設定できないため（F-08）

| 項目 | 内容 |

| 応答内容 | 営業時間・定休日・次回の臨時休業予定 |
| データ源 | 固定文（定型文） |
| 注意 | **F-08の臨時休業モードが有効な場合は、休業の案内を優先表示する** |

#### F-03　メニュー・料金の自動回答

| 項目 | 内容 |
|---|---|
| データ源 | **P-03で受領する紙メニュー表**（正本） |
| 表記ルール | **「〇〇円〜」と幅を持たせて表示する** |
| 必ず併記する注意書き | ①ロングは +1,000円 ②カット＋カラー同時は割引あり ③正確な金額は施術時にご案内 |

> ⚠️ **料金を断定表示しないこと。** ロング料金とセット割引があるため、単一の金額で回答すると誤案内となり、クレームに直結します。

#### F-04　所要時間の自動回答

メニューごとの目安時間を定型文で回答する。こちらも「約〇分〜」と幅を持たせる。

#### F-05　空き状況の一次受け＋オーナーへの即時通知 ★最重要

**本システムの中核機能。** 紙の手帳で管理されているため、**自動で空き状況を回答することはできない。**

処理の流れ：

```
お客様：「来週の土曜って空いてますか？」
　↓
bot（即時・自動）：
　「ありがとうございます。空き状況を確認して、
　　オーナーより改めてご連絡いたします。
　　（本日19時以降のお問い合わせは、翌営業日のご連絡となります）」
　↓
オーナーのLINEへプッシュ通知：
　「【空き状況の問い合わせ】
　　お客様：〇〇様
　　内容：来週の土曜って空いてますか？
　　受信：11/7 22:14」
```

| 要件 | 内容 |
|---|---|
| 応答速度 | **3秒以内**に一次応答を返す |
| 通知先 | オーナー様のLINE（プッシュメッセージ） |
| 通知内容 | お客様の表示名・問い合わせ原文・受信時刻 |
| 営業時間外の文言 | 「翌営業日のご連絡となります」を自動で付与する |

> 💡 **この機能が「返信忘れ」を解消します。** お客様には必ず一次応答が返るため放置が発生せず、オーナー様には通知が残るため見落としが起きません。

#### F-06　予約の変更・キャンセルの即時転送 ★最重要

| 要件 | 内容 |
|---|---|
| 判定 | 「キャンセル」「変更」「予約」等のキーワード、またはボタン選択 |
| bot応答 | 「承知いたしました。オーナーより至急ご連絡いたします。」 |
| 通知 | **【至急】を冠してオーナーへプッシュ通知** |
| 禁止事項 | **botが変更内容を確定させてはならない** |

#### F-07　想定外の質問の転送

ボタン外・キーワード外の入力は、**推測して答えず**転送する。

```
「お問い合わせありがとうございます。
　こちらはオーナーが確認のうえ、改めてご返信いたします。」
```

#### F-08　臨時休業モードの切り替え

| 要件 | 内容 |
|---|---|
| 操作者 | オーナー様 |
| 操作方法 | **スマホのリッチメニューから**（オーナー様はPCが苦手） |
| 動作 | 有効時、F-02の回答冒頭に休業案内を挿入する。**F-05・F-06の一次応答にも添える** |
| 想定頻度 | 年5〜6回＋夏季・年末年始 |

**操作の流れ**

```
［臨時休業を設定］を押す
　↓
入力欄に「休業 」が入った状態でキーボードが開く
　↓
オーナー様が続きを打つ　例）休業 11/20（金）は臨時休業をいただきます
　↓
以後、営業時間を聞かれると冒頭に ⚠️ 付きで表示される
　↓
［休業を取り消す］を押すと通常営業の案内に戻る
```

| 決めたこと | 理由 |
|---|---|
| **日付を選ばせず、自由に文章で書いていただく** | 「12/29〜1/3」「本日」「午前のみ」など、休みの形が一定ではない。日付選択にすると表現できない休みが出る |
| **設定前の案内に「まだ何も設定されていません」と明記する** | 書き方の見本を**設定済みの内容と読み違える**ことを防ぐ（通し確認で実際に起きた） |
| 取り消しの案内はオーナー様にのみ返す | お客様には届かない（応答メッセージのため） |

**どこに出すか**

| 用件 | 出す場所 | 理由 |
|---|---|---|
| 営業時間（F-02） | **いちばん上** | 「何時まで？」への答えとしては、**休みであることが最重要** |
| 空き状況・予約の変更（F-05・F-06） | **お礼を述べたあとに「⚠️ なお、〜」** | お客様はまだ日にちを言っていない。**いきなり ⚠️ で始めると、断られたように読める** |
| ご相談（F-09） | **出さない** | お気持ちのお話に、休業の案内は関係がない |
| **続きの連絡（F-17）** | **出さない** | **直近のお返事で一度お伝えしている。**同じ警告を繰り返すと、かえって読み飛ばされる |

```
お問い合わせありがとうございます。

空き状況を確認して、オーナーより改めてご連絡いたします。

⚠️ なお、明日は急遽都合によりお休みをいただきます

▼ よろしければ、あわせてお送りください
・ご希望の日にちと時間帯（第2希望までいただけると助かります）
・ご希望のメニュー（カット／カラー など）
```

> **日時にかかわる用件で休業案内を添えるのは**、休みの日をご希望のまま話が進むと、お互いに無駄な往復が生まれるためです。
> **ご希望の日時を伺うより前**に置いているのも同じ理由です。

#### F-09　クレーム・お悩み相談の非応答

「髪が傷んだ」「似合わなかった」「相談したい」等を検知した場合、**botは内容に一切触れず**、オーナーへ転送する。

```
「ご連絡ありがとうございます。
　オーナーより直接ご返信いたしますので、少々お待ちください。」
```

#### F-10　未対応リストの管理（「対応済み」ボタン）★最重要

F-05〜F-07・F-09で転送したすべての問い合わせを**未対応として記録**し、オーナー様が「対応済み」ボタンを押すまで消えないようにする。

```
【空き状況の問い合わせ】
お客様：みわ様
内容：来週の土曜って空いてますか？
受信：11/7 22:14

　［ ✅ 対応済みにする ］
```

> ⚠️ **技術的な制約（重要）**
> LINEのWebhookは**お客様の操作でしか発生しません**。公式ドキュメントのWebhookイベント一覧に、**自アカウントが送信したメッセージに対応するイベントは存在しません**。
> そのため「**オーナー様が返信したら自動で未対応から消える**」は実現できません。
> ボタンを1回押していただく運用とし、その手間を最小にするため、**すべての通知にボタンを添えます**。

#### F-11　朝の未対応まとめ通知（1日1回）★最重要

| 項目 | 内容 |
|---|---|
| 送信時刻 | **毎朝8時台**（開店10時より前） |
| 送信条件 | **未対応が1件以上あるときのみ**。0件の日は送らない |
| 内容 | 未対応の件数・一覧・各件の「対応済み」ボタン |

```
おはようございます。
未対応のお問い合わせが2件あります。

① みわ様（11/7 22:14）
　「来週の土曜って空いてますか？」
　［ ✅ 対応済みにする ］

② たろう様（11/7 23:40）
　「明日の予約を変更したいです」
　［ ✅ 対応済みにする ］
```

> 💡 **これが「夜、返信のことが頭から離れない」への回答です。**
> 夜のうちに覚えておく必要がなくなり、**朝、開店前にまとめて片付ければよい**状態になります。

#### F-12　新規通知への未対応件数の同梱

新しい問い合わせを通知する際、**未対応が他に残っていれば冒頭に件数を添える**。

```
※ ほかに未対応が2件あります

【空き状況の問い合わせ】
お客様：たろう様
...
```

> 追加のメッセージを送らないため、**メッセージ通数を消費しません。**
> 日中のリマインドは、専用の再通知ではなくこの方式で代替します（F-11の制約を参照）。

#### F-13　「未対応」の照会

オーナー様がbotに「**未対応**」と送ると、現在の未対応一覧を返す。

| 項目 | 内容 |
|---|---|
| 費用 | **0円**（応答メッセージは無料メッセージ通数にカウントされない） |
| 用途 | 施術の合間などに、オーナー様が能動的に確認したいとき |

#### F-14　送信取消への対応

お客様が問い合わせの送信を取り消した場合、**保存している記録を削除**し、以後の通知対象から除外する。

> LINE公式ドキュメントでも、送信取消イベントの受信時は「データベースなどに保存している対象のメッセージを削除する」ことが推奨されています。

#### F-15　空き状況・変更時に、ご希望の日時を一緒に伺う（v1.2 追加）

一次応答で「確認します」と返すだけにせず、**この時点で必要な情報をまとめて伺う。**

```
空き状況を確認して、オーナーより改めてご連絡いたします。

▼ よろしければ、あわせてお送りください
・ご希望の日にちと時間帯（第2希望までいただけると助かります）
・ご希望のメニュー（カット／カラー など）
```

| | やり取りの回数 |
|---|---|
| 伺わない場合 | お客様「空いてますか？」→ オーナー「いつがご希望ですか」→ お客様「土曜の午後」→ オーナー「空いています」… **最低3往復** |
| 伺う場合 | お客様「空いてますか？」＋希望日時 → オーナー「空いています」… **1往復** |

> **オーナー様の手間を減らす効果は、自動回答よりこちらが大きい**と考えています。
> 既存客が8割を占めるため、実際に届く問い合わせの多くが空き状況と予約変更だからです。

#### F-16　同じお客様の未対応をひとつにまとめる（v1.2 追加）

同じお客様から続けて連絡が届いた場合、**既にある未対応に合流させる。**

| 考え方 | **お客様ひとりにつき、オーナー様が返す返事はひとつ。だから未対応もひとつ。** |
|---|---|
| 合流の対象 | 直近12時間以内の、同じお客様の未対応 |
| 合流したときの通知 | 「【追加のご連絡】…※ 先ほどのお問い合わせの続きです（未対応は増えていません）」 |

**例外：急ぎの用件に変わったときは別の1件とする**

```
「空き状況を知りたいです」（未対応①）
　↓
「やっぱりキャンセルで」    → 未対応②【至急】として通知
```

> 合流させてしまうと、**至急の連絡が前の問い合わせに埋もれて気づけなくなる**ためです。

#### F-17　続きの連絡と新しい質問を見分ける（v1.2 追加）

F-16で合流させる場合も、**お客様へお返しする文面は内容に合わせて変える。**

**新しいご用件とみなす条件（いずれかに当てはまれば）**

| # | 条件 | 例 |
|---|---|---|
| ① | **ボタンを押して送られた文面** | 「空き状況を知りたいです」「予約を変更したいです」 |
| ② | 用件が**ご相談**または**予約の変更** | 「髪が痛みました」「やっぱりキャンセルで」 |
| ③ | **問いかけの形をしている**（「？」「ですか」「ますか」等） | 「駐車場はありますか？」 |

当てはまれば**その用件の一次応答**を返し、当てはまらなければ**先ほどの補足**として短くお礼を返す。

| 届いた文面 | 判定 | お返しするもの |
|---|---|---|
| 「空き状況を知りたいです」 | ①ボタン | 空き状況の文面（ご希望の日時を伺う） |
| 「髪が傷んだ気がします」 | ②ご相談 | ご相談の文面（オーナーより直接ご返信いたします） |
| 「駐車場はありますか？」 | ③問いかけ | 一次応答（確認のうえ改めてご返信いたします） |
| 「土曜の午後が希望です」 | 補足 | 「ありがとうございます。あわせてオーナーにお伝えいたします」 |
| 「14時でカットでお願いします」 | 補足 | 同上 |

> **①が必要な理由**
> 「空き状況を知りたいです」と「土曜の午後が希望です」は、**どちらも空き状況にかかわる、問いかけの形でない文面**です。文章からは見分けがつきません。
> 唯一たしかな違いは「**ボタンの文面そのものかどうか**」です。**ボタンを押したということは、新しいご用件をお持ちだということ**だからです。
>
> ボタンの文面は `src/lib/buttons.ts` にまとめ、**リッチメニューを作るスクリプトとずれていないかを自動テストで確認**しています（ずれると、ボタンを押したのに補足扱いになるため）。

> ⚠️ **未対応をまとめるのはオーナー様側の都合です。その都合をお客様に見せてはいけません。**
> ご相談に「ありがとうございます。あわせてお伝えします」と返すのは、**内容を受け止めていないのと同じ**です。
> 新しい質問に同じ返し方をするのも、質問が流されたように見えます。

**オーナー様への通知も、続きであることと急ぎであることの両方を伝えます。**

| 用件 | 見出し |
|---|---|
| 予約の変更・キャンセル | **【至急・追加のご連絡】** |
| お悩みのご相談 | **【要対応・追加のご連絡】** |
| それ以外 | 【追加のご連絡】 |

#### F-18　「すべて対応済みにする」ボタン（v1.2 追加）

未対応が**2件以上**あるときのみ、一覧の下にまとめて片付けるボタンを表示する。

| 項目 | 内容 |
|---|---|
| 表示条件 | 未対応が2件以上（1件のときは個別ボタンで足りる） |
| 用途 | 朝まとめて返信を済ませたあと、**1タップで全件を片付ける** |
| 対象 | **一覧をお送りした時点で未対応だったものに限る** |

> F-10の「ボタンの押し忘れ」対策です。件数が増えるほど押す回数が増える問題を解消します。

> ⚠️ **「お送りした時点」に限る理由**
> 朝8時の一覧（3件）を見たあと、9時に新しい問い合わせが届き、10時にボタンを押す——という順序が起こります。
> このとき全件を消すと、**オーナー様がまだ見ていない9時の1件も消えてしまいます。**
> 「返信を忘れない」という本システムの目的を、システム自身が破ることになるため、**ボタンに「いつの一覧か」を持たせ、それより新しいものは残します。**
>
> ```
> 3件すべてを対応済みにしました。
>
> そのあとに届いた1件は残してあります。
> 「未対応」と送るとご確認いただけます。
> ```

#### F-19　臨時休業の取り消し忘れを毎朝お知らせする（v1.2 追加）

臨時休業のお知らせが出たままになっている場合、**毎朝のまとめ（F-11）に添えてお伝えする。**

```
⚠️ 臨時休業のお知らせが出ています
「11/20（金）は臨時休業をいただきます」
お休みが終わっている場合は、取り消してください。

　［ お知らせを取り消す ］
```

| 項目 | 内容 |
|---|---|
| 送信条件 | 臨時休業のお知らせが設定されているとき |
| 費用 | **0通**（F-11と同じ1回の送信にまとめるため。通数は送った相手の人数で数える） |

> **v1.1では第13章のリスク「臨時休業の切り替え忘れ」に対し、操作手順書で対応するとしていました。**
> しかし**人の記憶に頼る対策は、本システムが解決すべき課題そのもの**です。
> 「返信を忘れる」のと同じ構造なので、**同じ方法（毎朝お知らせして1タップで片付ける）**で解決します。

#### F-20　オーナー様専用リッチメニューの出し分け（v1.2 追加）

同じ公式アカウントのまま、**オーナー様だけ別のリッチメニューを表示する。**

| 対象 | 表示するもの |
|---|---|
| お客様 | 営業時間／メニュー・料金／施術時間／空き状況／予約の変更／その他（2段×3列） |
| **オーナー様** | **未対応の一覧／臨時休業を設定／休業を取り消す／使い方（1段×4列）** |

| 項目 | 内容 |
|---|---|
| 実現方法 | Messaging API の「ユーザー単位のリッチメニュー割り当て」 |
| 費用 | 0円（追加のアカウントも契約も不要） |

> オーナー様は**文字を打たずに操作できます。**「未対応」などの文字入力も引き続き使えます。

## 7. 非機能要件

| ID | 項目 | 要件 |
|---|---|---|
| N-01 | **正確性** | **AIによる文章生成を行わない。**すべて定型文で応答する |
| N-02 | 応答速度 | 一次応答は3秒以内 |
| N-03 | 稼働 | 24時間365日 |
| N-04 | **個人情報** | **電話番号・メールアドレス・住所・施術履歴は収集しない。**未対応管理に必要な最小限（LINEの識別子・表示名・問い合わせ本文・受信時刻）のみ保存する |
| N-05 | セキュリティ | Webhookの署名検証を行い、LINE以外からのリクエストを遮断する |
| N-06 | 運用性 | 臨時休業の切り替えはスマホから操作可能であること |
| N-07 | 費用 | 月額の実費を1,000円以内に収めること |
| N-08 | **データ保持** | 対応完了から**30日で自動削除**する。お客様が送信を取り消した場合は**即時削除**する |

> **N-01について**：オーナー様の最優先要望は「間違った料金を伝えないこと」です。AIの自由回答は自然な一方で誤答の可能性があるため、**採用しません**。

> **N-04について（v1.1で変更）**：当初は「一切保存しない」方針でしたが、**未対応を追いかける以上、記録を持たざるを得ません**。そこで「保存しない」ではなく「**必要最小限だけ持ち、短期間で消す**」方針に変更しました。
> 保存するもの：LINEの識別子・表示名・問い合わせ本文・受信時刻・対応状況
> **保存しないもの：電話番号、メールアドレス、住所、施術履歴**
> 最終的なやり取りはオーナー様が直接行うため、これ以上の情報は不要です。

## 8. スコープ外（本件では作らないもの）

**ここに書かれていないものは作りません。**追加のご要望は別途お見積もりとなります。

| 項目 | 理由 |
|---|---|
| **空き状況の自動回答** | 予約が紙の手帳で管理されているため、システムから参照できない |
| **予約の確定・変更の自動処理** | ダブルブッキング防止のため、最終判断はオーナー様が行う |
| **「空いている時間帯を選んで予約する」機能** | 下記のとおり、予算・運用の両面で本件に合わないため見送り |
| **予約台帳のシステム化** | 本件の予算規模を大きく超える |
| **お電話での問い合わせ対応** | LINE以外は対象外 |
| **Instagram DMへの対応** | 同上 |
| **AIによる自由回答** | N-01により不採用 |
| **決済・キャッシュレス対応** | 要望なし |
| **多言語対応** | 要望なし |
| **料金表そのものの作成・整理** | P-03によりオーナー様からご提供いただく |
| **オーナー様の返信を自動で検知すること** | **LINEの仕様上、実現不可能。**Webhookはお客様の操作でのみ発生し、オーナー様の送信はシステムに通知されない。代わりに「対応済み」ボタンを用いる（F-10） |
| **1日2回以上の自動リマインド** | Vercelの無料プランは定時実行が1日1回に制限されるため。F-11（朝1回）とF-12（通知への同梱）、F-13（任意の照会）で補う |

> **「空いている時間帯を選んで予約する」機能について（ご相談への回答）**
>
> | 項目 | 見込み |
> |---|---|
> | 追加の開発費 | **+10〜15万円**（予約台帳・空き枠の計算・重複防止・変更取消の整合） |
> | 追加の月額 | **5,000円程度**（予約確定・前日確認の通知で無料枠200通を超えるため、ライトプランへの変更が必要） |
> | 運用上の前提 | **紙の手帳をやめ、すべての予約をシステムに入れていただくこと** |
>
> 最大の問題は3つ目です。紙の手帳とシステムが並走すると、**どちらにも入っていない予約が生まれ、ダブルブッキングが起きます。**
> ご予算（3万円）と「今の進め方を大きく変えたくない」というお話から、**本件では見送る**と判断しました。
> 将来ご検討される場合は、**予約台帳のシステム化から**着手するのが順序です。

## 9. システム構成

```
お客様のLINE
　　↕
LINE Messaging API
　　↕ Webhook（署名検証あり）
アプリケーションサーバー（Next.js / Vercel）
　　↕
データベース（Supabase）… 未対応の記録のみ・30日で自動削除
　　↓ プッシュ通知 ／ 毎朝8時台の定時実行（Vercel Cron）
オーナー様のLINE
```

| 要素 | 採用技術 | 備考 |
|---|---|---|
| 応答処理 | Next.js（App Router）／TypeScript | |
| ホスティング | Vercel（無料プラン） | |
| **データ保存** | **Supabase（無料プラン）** | 未対応の記録のみ。定型文はコード内に保持 |
| **定時実行** | **Vercel Cron（1日1回・毎朝8時台）** | F-11の朝のまとめ通知 |
| 臨時休業フラグ | データベース上の設定値 | スマホから切替可能にする |

### 費用の考え方

| 項目 | 月額 | 根拠 |
|---|---|---|
| LINE メッセージ費用 | **0円** | 下表のとおり**最大120通/月**。コミュニケーションプランの無料枠**200通**に収まる |
| サーバー費用 | **0円** | Vercel 無料プラン |
| データベース費用 | **0円** | Supabase 無料プラン |
| **合計** | **0円** | ご希望の「月額1,000円以内」を満たす |

**メッセージ通数の内訳**

| 用途 | 種別 | 通数 |
|---|---|---|
| F-01〜F-04・F-13（お客様・オーナー様への返信） | 応答メッセージ | **0通**（カウント対象外） |
| F-05〜F-07・F-09（オーナー様への即時通知） | プッシュ | 約90通/月（1日3件想定） |
| F-11（朝のまとめ） | プッシュ | 最大30通/月（未対応がある日のみ） |
| F-12（未対応件数の同梱） | ― | **0通**（既存の通知に文字を足すだけ） |
| **F-16（追加のご連絡）** | プッシュ | 約10通/月（未対応が増えない代わりに通知だけ送る） |
| **F-19（臨時休業のお知らせ）** | ― | **0通**（F-11と同じ1回の送信にまとめる） |
| **合計** | | **最大130通/月**（無料枠200通に対し余裕70通） |

> **通数は「送った相手の人数」で数えます。** 1回の送信に複数のメッセージを入れても1通です。
> F-19 を F-11 と同じ送信にまとめているのは、この性質を利用して通数を増やさないためです。

> ⚠️ **Vercel無料プランの制約について**
> 公式ドキュメントにより、無料プランの定時実行は**1日1回まで**、実行時刻には**±59分の誤差**があります。
> そのため「2時間後に再通知」のような複数回リマインドは行わず、**F-11（朝1回のまとめ）＋F-12（通知への同梱）＋F-13（任意の照会）**の3点で補う設計としています。
> 1日複数回の自動リマインドが必要な場合、Vercel Proプラン（月額約3,000円）への変更が必要となり、ご予算を超えます。

> 無料枠200通を超える見込みが出た場合は、事前にご相談のうえ対応を検討します。

| 臨時休業の切り替え忘れ | 誤案内が発生する | **v1.2で機能として解決**。毎朝のまとめに「お知らせが出ています」と1タップの取り消しボタンを添える（F-19）。**人の記憶に頼らない** |
| **「対応済み」ボタンの押し忘れ** | 対応済みの件が翌朝も通知される | **誤通知は放置より実害が小さい**ため許容する。朝のまとめからも直接押せるようにし、2件以上なら一括ボタンも出す（F-10・F-18） |

| **お客様の問い合わせが分断して見える** | オーナー様が同じ方に何度も返信する | 直近12時間の未対応に合流させる（F-16）。**急ぎの用件のときだけ別件にする** |

### 15-4. 学んだこと

**8件すべて自動テストに追加済みです**（合計55件）。同じ壊れ方は再発しません。

| | 分かること | 見つかったもの |
